# Calc spec 03: Land (footprint, exclusions, stations, gen-tie cost)

_P3 calc spec · area: land · 2026-10-15 · code read: `one-studio/app` (landcore.js, views/land.js, views/land-trace.js, api_land.py, gridrules.js, rules/isone.js, projects.js) · rules: `rules/isone-2026/interconnection.json` · REGISTER: `v8-isone-complete/research/REGISTER.md`._

## How the numbers here were produced

- **Every worked-example figure is script output.** It comes from `one-studio-devkit/tools/calc-spec/land.mjs`, run as `node tools/calc-spec/land.mjs --out docs/calc-spec/03-land.worked.json` from `one-studio-devkit`. The run's saved JSON is `docs/calc-spec/03-land.worked.json`. A reference such as `W:solar111209.corridor.cost` points at a key in that file.
- **The script reads only local files.**
  - The app's own calculators (`landcore.js`) and `data/land.json` / `data/samples.json`.
  - Dev-kit fixtures `bus__<id>.json.gz` and `x__land__site5__<id>.json.gz`. These are recorded `:8105` responses, i.e. the unified DuckDB read through `api_land.site()` and the Grid bus payload.
  - It needs no server and no DuckDB.
- **Two real buses with dummy-sample inputs.**
  - Solar: **Hatchville 111209** (Barnstable, MA), "Dummy — Cape Cod Solar", 100 MW.
  - Hybrid: **North Cambridge 110815** (Middlesex, MA), "Dummy — North Cambridge Solar + Storage", 150 MW export + 75 MW battery.
  - Land, line and permit inputs are the samples' `assumptions.ui.land` values from `plan/build_samples.py` L781–797. These are demo inputs, not quotes.
- **New pins.** `one-studio/app/tests/calc-spec-land.test.mjs` adds 4 tests (pass) and 2 `todo` pins for flags L-F1 and L-F2. The existing land suites still pass: 48/48 across land, land-core, land-fuel, land-v6, p2-land-verdict and p2-land-crossstage.
- **Sign rule.** No calculation in this area reads a price. The ISO-NE LMP = E + C + L sign rule does not apply here.
- **Null rule.** Throughout the area, a missing input yields `null` / "not held", never 0. Each section below states where this is enforced.

## A. Footprint (land need)

### A1. Land need, low / base / high
- **Where:** `landcore.js:footprint` (L14). The project MW comes from `views/land.js:projectMW` (L54): `importMW` for a data centre, otherwise `exportMW`.
- **Formula:** `need_band = acres_per_mw[band] × MW` for band ∈ {low, base, high}. It is null when the row is missing or MW ≤ 0. `cited`, `area_basis` and `source` are carried from the row.
- **Inputs:**

| Input | Unit | Source |
|---|---|---|
| `intensity.by_fuel[FUEL_KEY[tech]].{low,base,high}_acres_per_mw` | ac/MW (total fenced project area) | `data/land.json` `intensity` (generated by `tools/studio_land_intensity.py`) |
| MW | MW | user (project strip) |
| `FUEL_KEY` | n/a | storage→`bess`, datacenter→`dc` |

- **Assumptions:**

| Assumption | Source | Status |
|---|---|---|
| Solar 3.6 / 5.6 / 8.9 ac/MW (fixed-tilt median / single-axis median / 2013 capacity-weighted total) | Bolinger & Bolinger 2022 (IEEE JPV 12(2)); Ong et al. NREL/TP-6A20-56290 | cited, but read from a secondary extraction ("verify before client use", shown as a warning by `land-trace.js:verifyNote`) |
| Wind 30 / 85 / 140 ac/MW (mean ± 1σ) | Denholm et al. NREL/TP-6A2-45834, 2009 | cited (same verify caveat) |
| Storage 0.5 / 0.8 / 1.2 ac/MW (4-hour) | industry rule of thumb | assumed (`cited: false`) |
| Data centre 0.8 / 1.5 / 2.5 ac/MW | industry rule of thumb | assumed. Denominator (IT MW vs interconnection MW) unresolved, so **decision pending** |
| Hybrid 4.1 / 6.4 / 10.1 = solar + storage per band | row construction | assumed. Storage MW is taken = solar MW (see **L-F1**) |
| None of the land-intensity figures is in REGISTER | — | REGISTER has no land section (**L-F7**) |

- **Worked example (Hatchville, solar 100 MW):** row 3.6 / 5.6 / 8.9 gives need **360 / 560 / 890 ac** (`W:solar111209.footprint`). North Cambridge hybrid at 150 MW gives 615 / 960 / 1,515 ac (`W:hybrid110815.footprint`).
- **Tests:**
  - `tests/land.test.mjs` › "solar 100 MW needs 560 acres (base 5.6 ac/MW)".
  - `tests/land-core.test.mjs` › "needMatrix: every tech × size, linear in MW, blanks stay null".
  - `tests/calc-spec-land.test.mjs` › "hybrid intensity row = solar + storage per band" (new).

### A2. Need matrix and need curve
- **Where:** `landcore.js:needMatrix` (L166), plus `views/land.js:tabFootprint` (L198–207). Sizes `SIZES = 50…500 MW` (L60); the matrix shows 50, 100, 250, 500.
- **Formula:** `footprint(intensity, tech, mw)` for every tech × size. An unknown tech gives null bands. "Largest block holds base up to X MW" (`blockMax`, L218) is the largest size in `SIZES` whose base need ≤ block.
- **Inputs:** as A1. The sizes are hard-coded in the view (a UI sweep, not a rule).
- **Worked example:** linear in MW, e.g. solar 500 MW = 10 × solar 50 MW. This is pinned by the test, not run separately.
- **Test:** `land-core.test.mjs` › "needMatrix: …".

## B. Exclusions and buildable area

### B1. Layer state (null policy for screen layers)
- **Where:** `landcore.js:layerState` (L35) and `LAYER_SOURCE` (L25).
- **Formula:**
  - `acres` not finite → `missing` ("acres not held").
  - `acres = 0` and the layer's coverage is not declared (`e.coverage[layer]` → `LAYER_SOURCE[layer].covers` → false) → `missing` ("not screened here …").
  - Otherwise `ok` with `value = acres`.
- **Inputs:** `land.json exclusions[bus].layers[].{layer, acres, share, subtracted}` (Studio copy, `data-ext.js` exclusions) and the coverage declaration in `LAYER_SOURCE`.

| Assumption | Source | Status |
|---|---|---|
| Habitat = USFWS federal critical habitat only; state rare-species habitat (MA NHESP) not held, so 0 ac habitat = "not screened here" | S2-EM F007, `OVERLAY-ACQUISITION.md` | cited (coverage gap stated) |
| PAD-US protected, airport zones and DOE NETL 2024 energy-community cover all six states | `LAYER_SOURCE` | cited |

- **Worked example:** Hatchville habitat has 0 ac with coverage undeclared, so `status: missing`, `value: null`, and `unscreened = ["habitat"]` (`W:solar111209.screen.layers[0]`, `.unscreened`).
- **Test:** `tests/s2em-core.test.mjs` (layerState / landStatus / siteExclusionNote cases).

### B2. Screen and excluded share
- **Where:** `landcore.js:screen` (L44).
- **Formula:**
  - `gross = disc_acres`
  - `clear = clear_acres`, labelled the "largest block outside habitat/protected land"
  - `excludedShare = 1 − clear / gross` (null if gross ≤ 0 or either value is missing)
  - Layers split into `subtracted` (habitat, protected) and `advisory` (airport, energy-community)
  - `unscreened` = subtracted layers whose state is missing
- **Inputs:**

| Field | Unit | Source |
|---|---|---|
| `radius_mi` | mi (3, 5 or 8; 81 / 3 / 82 buses) | Studio copy |
| `disc_acres` | ac | measured on projected geometry, EPSG:26919 |
| `clear_acres` | ac | **largest contiguous clear block**: `analytics-analyzer-studio-preview/tools/studio_export.py` L776 writes `clear_acres = largest_contiguous_clear_acres`, from `land_overlay.py:_measure` |
| `clear_blocks` | count | same export |
| `water_excluded` | bool | false on all 166 screens |

| Assumption | Source | Status |
|---|---|---|
| Only habitat and protected land are subtracted; water, urban land, wetlands and slope are not, so the block is an upper bound | `FIT_CAVEAT` | assumed, labelled |
| UTM 19N used for buses west of 72°W (~0.2% area scale error) | `land-trace.js:utmNote` | assumed, labelled |
| Screens held for 166 of 2,678 spine buses; an unscreened bus is "not screened", never clear | `land.json`; spine count from `landCost.meta.coverage.spine_buses` | cited |

- **Naming trap (not a defect):** in the analyser's live `measure_disc()` API, `clear_acres` is the **sum** of clear blocks. The exporter that wrote `land.json` mapped the **largest** block into that same key. Any new extraction must keep that mapping, or every "fits" turns optimistic.
- **Worked example (Hatchville):** 3-mi disc, gross **18,093.8 ac**, block **9,591.8 ac**, 31 blocks, water not excluded. `excludedShare` = 1 − 9,591.8 / 18,093.8 = **0.469885** (`W:solar111209.screen`).
- **Tests:**
  - `land.test.mjs` › "Mashpee screen: largest clear block 11,913.1 acres of a 3-mile disc".
  - `calc-spec-land.test.mjs` › "screen.excludedShare = 1 − largest block ÷ disc" (new).

### B3. Disc area check
- **Where:** `landcore.js:discAcres` (L54). Used in `land-trace.js:traceArea` as an independent check.
- **Formula:** `π · r² · 640` (ac per mi² = 640).
- **Worked example:** r = 3 gives **18,095.6 ac** against the measured 18,093.8 (`W:solar111209.discAcres`), a 0.01% difference.
- **Test:** `land.test.mjs` › "disc acres = π·r²·640 within 0.1% on every held screen".

### B4. Net excluded range
- **Where:** `landcore.js:excludedRange` (L142). Shown in `views/land.js` KPI "Excluded, habitat + protected only" (L123).
- **Formula:**
  - `s` = finite `acres` of the subtracted layers
  - `low = max(s)` (0 if none)
  - `sum = Σ s`
  - `high = min(sum, gross − clear)` when clear is held, else `min(sum, gross)`
  - The KPI shows `100·low/gross` – `100·high/gross` %
- **Assumption:** layers overlap, so the net share is a range (assumed, labelled).
- **Worked example (Hatchville):** protected 8,392.5, habitat 0, so low = high = sum = **8,392.5 ac** (46.4%) (`W:solar111209.excludedRange`).
- **Test:** `land-core.test.mjs` › "excludedRange: lower = largest layer, upper = min(sum, disc − block)".
- **Flag L-F3:** the trace (`land-trace.js:traceArea` L31) prints the upper bound as `min(sum, gross)`, without the `gross − clear` cap the KPI uses.

### B5. Disc composition (ring)
- **Where:** `landcore.js:discSplit` (L151).
- **Formula:**
  - `excludedMin = min(excludedRange.low, gross − clear)`
  - `rest = gross − clear − excludedMin`
  - block + excludedMin + rest = gross
- **Worked example (Hatchville):** block 9,591.8 + certainly excluded 8,392.5 + rest **109.5 ac** (fragments or other exclusions) = 18,093.8 (`W:solar111209.discSplit`).
- **Test:** `land-core.test.mjs` › "discSplit: block + certain exclusion + remainder = disc; Mashpee".

### B6. Fit (does the need fit the block?)
- **Where:** `landcore.js:fit` (L58) and `fitLabel` (L65). Decision reuses it (`decisioncore.js` L132, gate "Land fit" L197).
- **Formula:**
  - Per band: `clear ≥ need[band]` → "fits", else "does not fit". A missing need gives "unknown".
  - `status = base band`.
  - No footprint or no screen gives "unknown" (never a pass).
  - `screenOnly: true` always. The caveat names water and the unscreened layers.
- **Worked example (Hatchville 100 MW solar):** 9,591.8 ≥ 890 / 560 / 360, so **fits / fits / fits**, with `unscreened: ["habitat"]` (`W:solar111209.fit`). Decision reads this as Hold (screen-only), never Pass.
- **Tests:**
  - `land.test.mjs` › "no exclusion screen gives unknown fit, never a pass".
  - `land.test.mjs` › "fit carries the habitat/protected-only caveat when water is not screened".

### B7. Block cover and base need as a share of the block
- **Where:** `landcore.js:blockCover` (L158). The gauge's `useB` / `useH` are inline in `views/land.js:tabArea` (L129).
- **Formula:**
  - `cover[band] = clear / need[band]`, null when either is missing or need ≤ 0.
  - Status: base ≥ 1 → "fits".
  - Gauge: `useB = 100 · need_base / clear`.
- **Worked example (Hatchville):** cover **26.64 / 17.13 / 10.78×** (low / base / high), and base need = **5.84%** of the block (`W:solar111209.blockCover`, `.baseNeedPctOfBlock`).
- **Tests:** `land-core.test.mjs` › "blockCover: ratio per band; no screen → null ratios, never a pass". The gauge `useB` is inline in the view with no unit test (**L-F9**).

### B8. Land status for Market shortlists, and screen count
- **Where:** `landcore.js:landStatus` (L71) and `landScreenCount` (L81).
- **Formula:**
  - `fit(footprint(…), screen(…))` mapped to "fits*" / "does not fit" / "unknown: …", with "(X not screened)" appended.
  - No data → "land data not loaded"; no screen → "land not screened".
  - `landScreenCount` = buses in the list that hold a screen.
- **Worked example:** Hatchville gives **"fits* (habitat not screened)"** (`W:solar111209.landStatus`).
- **Test:** `s2em-core.test.mjs` (landStatus / landScreenCount cases).

### B9. Screened neighbours: block share
- **Where:** `views/land.js:neighbourRows` (L105), inline.
- **Formula:** `share = 100 · clear / gross` per screened bus. "fits*" when `clear ≥ need_base`. Distances are the API's `screened[].mi`: haversine from `dim_substation`, nearest 15 screened buses (`api_land.py` L133–136).
- **Inputs:** `land.json` exclusions; API `screened`.
- **Test:** no unit test (inline). The same arithmetic as B2 / B6 is covered there (**L-F9**).

## C. Land cost

### C1. County land-cost proxy
- **Where:** `landcore.js:landRate` (L107).
- **Formula:** look up the row whose `STATE|COUNTY` (upper-case) equals the node's `state_code|county`. Missing gives null.
- **Inputs:** `land.json landCost.rows[].{state, county, low, base, high}` in $/acre (`derived.mart_land_cost_proxy`); the node's `county` / `state_code` from unified `dim_bus`.

| Assumption | Source | Status |
|---|---|---|
| One band, $3,000 / $8,000 / $20,000 per acre, on all 69 county rows (`W:landCostDistinctBands`, `W:landCostRows`); no measured price anywhere in the workspace | `landCost.meta.figure_source_note`, `method` | **placeholder**. Shown as a sensitivity labelled "assumption", never the headline. Not in REGISTER (**L-F7**) |

- **Worked example:** Barnstable, MA gives 3,000 / 8,000 / 20,000, provenance `assumption` (`W:solar111209.landRate`).
- **Test:** `land.test.mjs` › "county land cost is a flagged assumption".

### C2. Cost grid, purchase cost and annual lease
- **Where:** `landcore.js:costGrid` (L171). The KPI "Land purchase cost" (`views/land.js` L194) and "Annual lease at base need" (L243) are inline.
- **Formula:**
  - `cost[band][rate] = need[band] × rate` (null if either is missing).
  - Purchase = `need_base × buy`.
  - Annual lease = `need_base × lease`.
- **Inputs:** footprint (A1); county band (C1); user `buy` ($/ac) and `lease` ($/ac-yr).
- **Worked example (Hatchville, buy $25,000/ac):**
  - Base row costs **$1.68M / $4.48M / $11.2M / $14.0M** (county low / base / high / user).
  - Purchase = **$14,000,000**.
  - Annual lease at $1,500 = **$840,000/yr** (`W:solar111209.costGrid`, `.purchaseBase`, `.annualLeaseBase`).
- **Tests:** `land-core.test.mjs` › "costGrid: acres × $/acre per band; a blank rate is not held". The purchase and annual-lease KPIs are inline (**L-F9**).

### C3. Growing-annuity PV factor
- **Where:** `landcore.js:annuityFactor` (L176).
- **Formula:**
  - In general: `AF = (1 − ((1+g)/(1+r))^n) / (r − g)`, i.e. Σ_{t=1..n} (1+g)^(t−1)/(1+r)^t.
  - When |r − g| < 1e−12: `AF = n/(1+r)`.
  - Null if n < 1 or r ≤ −1.
- **Worked example:** r = 8%, g = 2%, n = 30 gives **13.666529** (`W:annuityFactor_8_2_30`).
- **Test:** `land-core.test.mjs` › "annuityFactor: closed form equals the loop sum".

### C4. Lease vs buy (NPV)
- **Where:** `landcore.js:leaseVsBuy` (L184). The per-year chart is inline in `views/land.js` L229.
- **Formula:**
  - `pvLease = acres · lease · AF(disc%, esc%, years)`
  - `buyCost = acres · buy`
  - `pvResale = buyCost · resale% / (1+disc)^years`, null when resale is blank
  - `netBuy = buyCost − (pvResale ?? 0)`, labelled an **upper bound** when resale is blank
  - `diff = pvLease − netBuy`
  - `breakevenLease = netBuy / (acres · AF)`
  - Term must be a whole number 1–99. Any blank input gives "not held" with a list of what is missing.
- **Inputs:** acres = base need; all other terms are user inputs (%, $/ac, $/ac-yr, years).
- **Assumptions:** resale is a nominal % of the purchase price; lease is paid in arrears, growing at esc% per year (assumed, labelled "your inputs").
- **Worked example (Hatchville, 560 ac; $25,000/ac buy; $1,500/ac-yr lease; 8%; 30 yr; 2% escalator; 50% resale):**
  - `pvLease` = **$11,479,884**.
  - `pvResale` = **$695,641**.
  - `netBuy` = **$13,304,359**.
  - Lease is cheaper by **$1,824,475**.
  - Break-even lease = **$1,738/ac-yr** (`W:solar111209.leaseVsBuy`).
- **Test:** `land-core.test.mjs` › "leaseVsBuy: needs every input; blank resale gives a buy upper bound, never a silent 0".

## D. Stations (alternative connection points)

### D1. Distance (great-circle)
- **Where:**
  - `landcore.js:miles` (L114).
  - Server side, `api_land.py:_hav` (L20): the SQL used for every radius filter and `mi` column.
  - `land-trace.js:eqMiles` (L17) is an equirectangular cross-check only.
- **Formula:** haversine, `2·R·asin(√(sin²(Δφ/2) + cos φ1 · cos φ2 · sin²(Δλ/2)))` with R = 3,958.8 mi. A missing coordinate gives null (never 0).
- **Inputs:** `dim_substation.latitude/longitude` (else `dim_bus`), cast `TRY_CAST(... AS DOUBLE)`; user site lat/lon.
- **Assumption:** straight-line distance between published coordinates. Proximity is not an electrical relationship (labelled).
- **Worked example:** Hatchville → Falmouth Tap 111408 gives JS **1.930717 mi** = SQL **1.930717 mi**. Hatchville → Mashpee gives 4.261545 = 4.261545 (`W:solar111209.havCheck`).
- **Tests:**
  - `calc-spec-land.test.mjs` › "miles: the JS haversine equals the API SQL haversine" (new).
  - `tests/p2-land-stations.py` (independent Python haversine count).

### D2. Station radius query and coverage
- **Where:**
  - `api_land.py:site` (L104–117). Radii `R_STATION 15`, `R_BUS 10`, `R_GEN 10`, `R_QUEUE 25`, `R_UPG 15` mi (L17). There is no row cap since P2 C40.
  - `landcore.js:stationCoverage` (L309).
- **Formula:**
  - Server: stations = `dim_substation` rows with a coordinate, `bus_id ≠ candidate`, `mi ≤ 15`, each with the five `fact_headroom` envelopes (`hr_sp_dis`, `hr_sp_chg`, `hr_sh_dis`, `hr_sh_chg`, `hr_ll_chg`) and its `fact_limiting_element` rows (`stationElements`).
  - Client: `truncated = rows < stationsTotal`. Without a total, `rows ≥ 60` counts as truncated. The effective radius is the farthest row returned.
- **Worked example:** Hatchville has **113 of 113** rows within 15 mi, not truncated. North Cambridge has 245 of 245 (`W:*.stationCoverage`).
- **Tests:**
  - `p2-land-verdict.test.mjs` › "C40 stationCoverage: a capped list is flagged with its effective radius; a full list is not".
  - `p2-land-stations.py` (DB-backed: 108 / 245 / 255 rows).

### D3. Station grouping
- **Where:** `landcore.js:stationGroups` (L199).
- **Formula:**
  - Group rows by `substation_name | nominal_kv | latitude | longitude`.
  - `mi = min`. Envelope fields, short-circuit MVA and outlets = group maximum (display only). `rows` keeps each bus for the per-bus verdict.
  - Drop the candidate's own station: same name **and** kV and < 0.05 mi.
  - Sort by distance.
- **Worked example:** Hatchville's 113 rows form **98 station groups** (`W:solar111209.stationGroups`).
- **Test:** `land-core.test.mjs` › "stationGroups: buses sharing name, kV and coordinate are one station; own station dropped".
- **Note L-F6:** a co-sited station at another kV is kept, at 0.0 mi. At North Cambridge, the 345 kV station heads the list at **0 mi**: its line tie is $0 and its per-mile figure is floored (`W:hybrid110815.nearestStations[0]`). This is by design (different kV); the trace says so.

### D4. Which cases a request reads, and at what MW
- **Where:**
  - `landcore.js:requestCases` (L219) → `gridrules.js:applicableCases` (L52).
  - `landcore.js:caseMW` (L226) → `gridrules.js:chargeMW` (L394).
- **Formula:**
  - Solar / wind read summer-peak and shoulder **injection** at export MW.
  - Storage / hybrid add **shoulder charge**. Storage is never charged at summer peak (PP5-6 §9, REGISTER "Storage charging study basis", verified).
  - A data centre reads large-load and summer-peak **withdrawal** at import MW.
- **Worked example (hybrid 150 + 75):** cases `summer_peak|discharge`, `shoulder|discharge`, `shoulder|charge` at **150 / 150 / 75 MW** (`W:hybrid110815.caseMW`).
- **Test:** `land-fuel.test.mjs` › "requestCases mirrors gridrules.applicableCases for every fuel", "hybrid charges at its battery size (importMW …)".

### D5. Connection verdict for the candidate and for each station (Grid's rule, D6.1)
- **Where:**
  - `landcore.js:landVerdict` (L270), `stationGrid` (L282), `stationVerdict` (L290).
  - These call `gridrules.js:caseTable` (L107), `binding` (L143) and `elementLimit` (L67).
- **Formula:**
  - Per case:
    - `governing` = the element-study limit (lowest positive `transfer_mw` over non-pre-existing facilities) where one is held.
    - Otherwise the `fact_headroom` envelope, with status "Envelope only" (Hold-class, never Fits or Does not fit).
    - With the case asked at MW: Fits when `MW ≤ governing` on element evidence.
  - Per direction: `binding()` gives Does not fit (an element breach) › Envelope only › Partly studied › Fits.
  - Overall: any Does not fit → **Does not fit**. All Fits → **Fits**. Otherwise the first Hold-class status present, in the order Hold, Envelope only, Partly studied, Not studied.
  - `hr` = the lowest `governing` over the applicable cases.
  - A grouped station is tested bus by bus. The best single bus stands for it (Fits › Hold-class › Does not fit, then higher `hr`), and cases are never mixed across buses.
- **Inputs:**
  - `fact_headroom.headroom_mw` (MW; envelope = headline element set, vintage unconfirmed, decision D-007).
  - `fact_limiting_element.{transfer_mw, pct_loading_no_transfer, monitored_facility}` (MW, %; the 2026-05 element study).
  - MW as entered.

| Assumption | Source | Status |
|---|---|---|
| Element study is the source of record; envelope is context only | D6.1 (v8 06-decisions, 2026-10-06) | decided |
| Which element set governs (two vintages) | D-007 | decision pending |
| `shoulder|discharge` element rows are mislabelled large-load injection, so never used | `elementLimit` L68 | assumed (store trap, labelled) |

- **Worked examples:**
  - Hatchville solar 100 MW: own verdict **Envelope only (Hold)**, `hr` **197.8 MW**, binding `summer_peak|discharge` (`W:solar111209.ownVerdict`). This matches the plan's acceptance figure, Hatchville 197.8 MW.
  - Nearest station, Falmouth Tap 115 kV at 1.931 mi: Envelope only, `hr` 186.2 MW.
  - North Cambridge hybrid: own verdict **Does not fit (element study)**, `hr` 110.9 MW on `summer_peak|discharge` (`W:hybrid110815.ownVerdict`).
- **Tests:** `p2-land-verdict.test.mjs`:
  - "C07/C41 landVerdict = Grid binding() per direction …"
  - "C07 envelope-only evidence is 'Envelope only (Hold)' …"
  - "C07 cross-stage …"
  - "C07 grouped station: the best single bus stands for it …"
  - Plus `p2-land-crossstage.test.mjs`.

### D7. Headroom per mile of tie
- **Where:** `landcore.js:perMile` (L324). Applied in `views/land.js:tabCorridor` L267 as `perMile(v.hr, d)`.
- **Formula:** `hr / max(miles, 0.5)` in MW/mi. Null when either is missing. The distance is straight-line from the placed site, or from the bus when no site is placed.
- **Assumption:** the 0.5-mi floor is a ranking convenience, not a cost (Studio 2.04). Status: assumed, labelled.
- **Worked example:** Falmouth Tap 186.2 MW / 1.931 mi = **96.44 MW/mi** (`W:solar111209.nearestStations[0].perMile`).
- **Test:** `land-core.test.mjs` › "perMile: headroom ÷ max(miles, 0.5); null headroom is null".
- **Flag L-F4:** the card subtitle says "solved envelope ÷ straight-line miles", and the chart title says "Headroom per mile (lower of … injection …)". The value is actually `v.hr`: the lowest **governing** figure, which is the element-study limit where one is held and the envelope otherwise.

### D8. Short-circuit percentile

- **Flag L-F8:** the trace result label hard-codes "Percentile among 2,648 publishing buses" (`land-trace.js` L244) instead of reading `rank.of`.

## E. Gen-tie (connection line) cost

### E1. Corridor cost (the KPI "Connection line cost")
- **Where:** `landcore.js:corridor` (L427). Called from `views/land.js:tabCorridor` L259 with `routeFactor = L.route ?? 1.2` (L258).
- **Formula:**
  - `d = miles(site, bus)`. No site → "not held" (never 0 mi).
  - `route = d × routeFactor` when the factor ≥ 1. A factor < 1 is rejected (`routeError`, route null).
  - Blank `$/mile` → "partial", cost null.
  - `cost = (route ?? d) × $/mile + (terminal ?? 0) + (crossings ?? 0)`.
  - Status is **priced** only when route, terminal and crossings are all held. Otherwise it is **partly priced**, a lower bound shown with "≥".
- **Inputs:**

| Input | Unit | Source |
|---|---|---|
| Site lat/lon | ° | user (or sample) |
| Bus `latitude/longitude` | ° | unified `dim_bus` / `dim_substation` |
| Routing factor | dimensionless (routed ÷ straight) | user, default **1.2** |
| $/mile | $/mi | user |
| Terminal works | $ | user |
| Crossings and easements | $ | user |

| Assumption | Source | Status |
|---|---|---|
| Routing factor 1.2 | `views/land.js` L258; the UI calls it a "placeholder (needs a source)" | **placeholder**. Not in REGISTER (**L-F7**) |
| No $/mile benchmark held | land-trace notes | not held. User input only |
| Line cost is linear in miles; no voltage-class or terrain term | `corridor` | assumed |

- **Worked example (Hatchville; sample site 41.62616, −70.56229; ×1.2; $2M/mi; $5M terminal; $0.5M crossings):**
  - Straight distance **0.69 mi**, routed **0.828 mi**.
  - Cost **$7,155,979** (= 0.828 × 2,000,000 + 5,000,000 + 500,000; the script's independent check is equal).
  - Without the terminal: **partly priced, ≥ $2,155,979** (`W:solar111209.corridor`, `.corridorNoTerminal`).
  - North Cambridge: 0.6872 mi → **$7,149,349** (`W:hybrid110815.corridor`).
- **Tests:**
  - `land.test.mjs` › "no site location means distance not held, never zero", "missing terminal cost makes the corridor cost a lower bound", "blank crossings keep the corridor partly priced …", "routing factor below 1 is rejected …".
  - `calc-spec-land.test.mjs` › "corridor priced: cost = straight miles × routing factor × $/mile + terminal + crossings" (new).
- **Flag L-F2:** the project form field `route` (`projects.js` FIELDS L39) is labelled **"Gen-tie distance"**, unit **mi**, rule **≥ 0**. `corridor` reads the same key (`assumptions.ui.land.route`) as the **routing factor** (dimensionless, ≥ 1). A user who types a distance of 3 mi multiplies the straight line by 3. A value of 0.5 passes the form and is then rejected by Land. Pinned as a `todo` in `calc-spec-land.test.mjs`.

### E2. Tie cost per alternative station (alternatives table)
- **Where:** `views/land.js:tabCorridor` L300, `tieCost`, inline.
- **Formula:** `d × rf × $/mile`. Line only: no terminal and no crossings (labelled in the card footer). `d` is measured from the placed site, else from the bus.
- **Worked example (Hatchville):**
  - Falmouth Tap 1.931 mi × 1.2 × $2M = **$4,633,722**.
  - Mashpee 4.262 mi gives **$10,227,707** (`W:solar111209.nearestStations[*].tieLine`).
- **Test:** no unit test (inline; **L-F9**).
- **Note L-F11:** the station list is the API's 15-mi radius **from the bus**. Once a site is placed, distances are re-measured from the site, so a listed station can sit beyond 15 mi of the site, and a closer one outside the bus radius is missing. The column header says "Miles from site", but the card title still says "within 15 mi".

### E3. Line-cost sensitivity grid
- **Where:** `landcore.js:lineCostGrid` (L327). Levels are set in `views/land.js` L313–315: `STUDIO_PER_MILE = $1M, $2M, $3M, $4M/mi` (L61) plus the user entry; `FACTORS = 1, 1.15, 1.3, 1.5` (L62) plus the user's factor. Miles = site → bus, or bus → nearest station when no site is placed (L311).
- **Formula:** `cell = miles × factor × $/mile`. A factor < 1 or a blank gives null.

| Assumption | Source | Status |
|---|---|---|
| $1M–$4M/mi rows | the live Studio slider range | **placeholder** (labelled "assumption, not a quote"); not in REGISTER (**L-F7**) |
| Factors 1 / 1.15 / 1.3 / 1.5 | the Studio route allowances 0 / 15 / 30 / 50 % | assumed |

- **Worked example (Hatchville, 0.69 mi):** at $2M/mi, ×1 / 1.15 / 1.3 / 1.5 = **$1,380,000 / $1,587,000 / $1,794,000 / $2,070,000** (`W:solar111209.lineCostGrid[0]`).

## F. Site control and permit timing (on the Land stage)

### F1. Site-control gate
- **Where:** `landcore.js:siteControl` (L98) → `rules/isone.js:siteControlGate` (L161). This is shared with Queue and Decision.
- **Formula:**
  - `required = 100 × rule.value`. Pass when `pct ≥ required`.
  - If short, Pass via the deposit in lieu only when it is eligible: NRIS plus a recorded regulatory limitation.
  - Otherwise Fail. Blank → Open (never passes). Data centre → n/a.
- **Inputs:** user % under control; `interconnection.schedule22.site_control_at_request.value = 1.0` (Sched 22 §3.4.2, **corrected**, REGISTER L19); pro forma `0.9` (Order 2023 pro forma §3.4.2, verified, labelled profile only); deposit in lieu $10k/MW, $500k–$2M (REGISTER L18, verified).
- **Worked example:**
  - Sample 60% → **Fail**, required 100% (`W:solar111209.siteControl`).
  - 99% → Fail under ISO-NE.
  - 90% → **Pass** under the pro forma profile (`W:*.siteControl99`, `.siteControlProforma90`).
- **Test:** `land.test.mjs` › "site control is not applicable to a data centre (load), a gated percentage elsewhere". The rules engine has its own suite.
- **Minor L-F5:** the `landcore.js` comment (L94) cites "Sched 22 §3.4". The rule and REGISTER cite §3.4.2.

### F2. Permit timing and the permit window
- **Where:** `landcore.js:permitTiming` (L405), `permitTimeline` (L414), `permitCounts` (L390). The window span is inline in `views/land.js:tabPermits` L376.
- **Formula:**
  - Each item's offset and duration come from `po_<id>` / `pd_<id>`, else the index keys `po<i>` / `pd<i>`. A blank is null.
  - Task start = month `start + offset`; end = `start + offset + dur`. A blank duration is open-ended; a blank offset is not placed.
  - Window = months from the earliest start to the latest dated end, a lower bound when items are undated.
- **Inputs:** user month `YYYY-MM` and months per item. The checklist comes from general knowledge (`PERMIT_DISCLAIMER`): assumed, labelled "not a legal determination".
- **Worked example:**
  - Hatchville solar (9 items, sample `po_i = 2i`, `pd_i = 6 + 2·(i mod 4)`, start 2027-01): **9 of 9 dated, 26 months**.
  - Hybrid: 13 of 13, 34 months (`W:*.permitWindow`).
- **Tests:**
  - `p2-land-verdict.test.mjs` › "C44 permitTiming dates every checklist item …".
  - `land-core.test.mjs` › "permitTimeline …", "permitSummary …".
  - `land-fuel.test.mjs` › "permitList …", "permitRows …".
  - The window span is inline with no unit test (**L-F9**).
